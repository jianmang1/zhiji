# ADR-006：跨用户 Cohort 分析的权限边界

- 状态：Accepted（权限边界已定；跨用户聚合实现仍冻结，待 PO 隐私裁定）
- 日期：2026-10-21
- 决策人：Tech Lead（边界已裁定）；跨用户聚合是否/如何上线 → PO（隐私与合规）

## 背景

Phase 3 backlog A5 提出跨用户 cohort 汇总。当前 `getFunnel` 以调用者 JWT 查询 `analytics_events`，所有业务查询受 `user_id = auth.uid()::text` RLS 限制；因此当前漏斗只包含调用者自己的事件。引入跨用户统计会改变隐私边界，不能由普通用户请求任意 cohort 数据。

## 决策范围

本文仅定义进入实现前必须满足的权限规则，不批准跨用户聚合的实现或上线。

### 已决定的边界

1. ADR-006 被 Tech Lead 标记 **Accepted** 前，不得实现跨用户 cohort 查询、服务端 `service_role` 聚合或放宽现有 RLS。
2. 当前 `getFunnel` 继续使用调用者 JWT；输出只基于该 JWT 可见的数据。
3. 未来任何 cohort 接口必须限定在预先定义的 cohort 集合，不接受客户端任意提交用户 ID 列表或过滤表达式。
4. 管理权限须通过服务端受信任角色验证；不能以客户端传入的 `user_type`、渠道或“内部用户”字段作为授权依据。
5. 需在实现 ADR 中明确最小 cohort 样本量、可用维度、时间范围、数据保留及审计策略，并证明响应不能反推出单个用户事件。

## 待裁定事项

- cohort 看板是否仅供 Tech Lead/运营管理员，或对普通用户提供匿名聚合指标。
- 可信管理员身份的来源与撤销方式。
- 最小 cohort 数量阈值及低样本抑制策略。
- 是否需差分隐私或其它统计披露控制。
- 单独使用 `service_role` 的云函数与只读视图/RPC 哪种实施方式更合适。

## 影响

- A5 当前仅完成权限设计草案；跨用户聚合保持未实现。
- A1 的渠道质量、趋势和 A/B 返回值仍严格受当前 RLS 数据范围约束。
- Tech Lead 裁定后应新增实现 ADR/迁移计划，并按契约变更流程评审。

## 裁定记录（Tech Lead，2026-10-21，随 PR #9 合并）

- 边界规则 1–5 **接受为硬约束**：在 PO 就"是否/如何上线跨用户 cohort"拍板前，任何分支不得实现跨用户聚合、不得引入 `service_role` 越权查询、不得放宽 RLS、不得接受客户端任意 cohort 表达式。
- 当前 `getFunnel` 维持调用者 JWT + RLS 可见范围，Phase 3 A1 增强字段（`channel_quality`/`trend`/`experiments`）严格限于该范围，已随 PR #9 合并并写契约 §8。
- **待 PO 裁定（隐私/合规类升级）**：§"待裁定事项"中 cohort 看板受众、可信管理员身份来源、最小样本抑制、差分隐私、实施方式——属上线合规，须升 PO，不在 Agent 自驱范围。
